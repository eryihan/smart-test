# 范围发现与测试实施

按用户范围推进，局部 changes/check 不要求全仓画像、init 或项目登记。已有约束继续适用；缺少业务资料时恢复任务所需理解，不默认接管完整业务文档。长期资料仅在 [变化触发维护](artifacts.md#变化触发维护) 时处理。

## Repository Discovery / doctor

确认仓库根、已有改动、语言/运行时、构建入口与模块边界。搭建或全仓优化时核对框架、依赖管理、配置、迁移、API/message 协议和 CI；局部任务直接读相关文件。

批量查询确实省工作时使用 `inspect_repo.py --repo <repo> --path <范围> --query overview|build|tests|changes`；path 可重复，tests 超出展示上限会列出省略数量。默认输出紧凑事实；`--details` 用于需要详细静态证据与指纹的情况。工具不生成完整调用图或业务地图，Maven 继承/profile、Gradle 动态逻辑和运行时 wiring 由 Agent 核对。查询范围内的源码不代表其他范围已分析；全仓变更与消费者提示须按实际影响核查。

doctor 默认只读工具和配置，不运行构建、拉镜像或探测外部实例。分别核对 Docker 可执行文件与 daemon；未知环境标 UNKNOWN。只对本次必需动作评估 READY/WARNING/BLOCKED，缺 Docker 不阻止 Unit，缺隔离数据库不以 H2/mock/skip 冒充真实 DB 验证。

## 按项目选择方案

选择说明：项目事实 → 行为风险/已有缺口 → 所需边界 → 复用/新增设施 → 环境、执行和维护成本。技术复杂性与业务损失分别判断，不用代码行数、包名或 class 后缀打分。

已有兼容框架优先保留；必要能力缺失时只补相应 engine、插件、隔离和 fixture。无框架时给适配运行时与构建的最小方案；Java 接入见 [java-testing.md](java-testing.md)。无需替换时不枚举全部替代方案，不预装所有工具。覆盖率沿用已有门禁，未要求时不新增工具或数字阈值。

## init

评估现有测试的发现、断言、真实边界和可执行性，复用成熟设施，补必要能力。形成项目适用的测试策略：规则、接口、持久化/事务、异步/并发、契约、关键流程按实际风险选择，不固定比例。

在现有生效规范中保存长期约定、依据、运行入口、隔离和质量门。没有规范时才在正式文档位置建立；不登记管理状态、不生成整套画像或审批文件。已有业务文档直接关联；完整业务梳理只在明确请求时开展。

用有业务断言的代表性测试验证接入，分别报告 UT/IT 和未验证能力。无法运行时交付方案与未执行范围，不把设施或规范完成当验证通过。init 不默认改生产逻辑、迁移或正式 CI，也不要求一次补完存量缺口。

## scan

按范围梳理业务入口、消息、定时任务及相关测试，全仓 scan 默认覆盖全仓。分区导航用于本轮评估；区分已盘点、已读代码、已审查断言和未检查范围，不声称扫描文件即完成全部业务分析。

按 [已有测试评估](test-design.md#评估已有测试) 找行为、输入、断言与真实边界缺口。每条建议有证据、预期来源、缺口、测试边界、环境前提和优先原因；未知业务结果明确列出。高损失失败、权限/资金、状态与事务等依实际业务影响排序，简单逻辑也可能高风险。

默认分析，不改测试/业务、不运行构建。交付风险、已有保护、第一批范围及后续顺序；需要分批接续时维护现有当前事项，纯一次性分析可以对话交付。明确只读/dry-run 不落盘。分析完成不代表测试通过。

## changes

默认 HEAD 到工作树含 staged/unstaged 和未忽略 untracked。`--staged` 只分析索引；`--base <ref>` 为 merge-base 到工作树含未提交变更。用户指定 PR 提交范围时按实际范围取 diff，不混入无关修改。

先读文件清单和真实 diff，包括删除/重命名两侧、配置、Mapper XML、迁移、测试与协议；无变更不自动切 scan。追踪调用方、注入/代理/事件、模块消费者和跨服务影响。公共模块、根构建或安全基础配置可能要求扩大验证；动态关系不确定时保守扩大，不能仅凭静态提示选择精确测试集。

关联行为与已有测试，补强缺口；接续已有发现时更新对应事项。计划在当前任务内，只有实际消费者需要时独立保存。只要求计划就交付计划；授权补测试时继续实施、验证与归因。

staged 与实际工作树执行可能不同；清楚标识测试版本，或使用经授权的隔离快照，不自动 stash/drop。

## implement

核对预期、边界、环境和授权，保留用户与并发修改，局部且幂等地补丁。已有测试/fixture/插件足够时先扩展。生产修复须明确业务依据、正确测试和违反依据的证据，并在对应授权内应用；为测试改接口或注入 Clock 同属生产修改。

失败保留可审阅 diff 与实际结果。撤销只限本轮且未被他人改写的内容，不全仓 reset/clean。无法确定预期时暂停相关断言，继续独立工作；环境缺失不阻止已具备依据和 API 的实现及 Unit。验证见 [verification.md](verification.md)。

## dry-run

只读分析与对话交付，不写文件/锁，不创建 fixture、构建产物或服务，不调用执行器。已有资料可以只读核查；拟命令与结果分开，不写预计退出码或补造通过证据。
