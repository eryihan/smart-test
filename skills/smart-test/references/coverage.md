# 覆盖率策略

覆盖率衡量代码执行范围，与业务断言、接口契约、数据库约束和关键流程分别验证。使用仓库已有的 JaCoCo、Gradle、Maven 或原生工具采集，smart_test 记录策略、核对报告并判定门禁。

## 策略输入

长期要求写入生效项目规范，本次要求在当前任务说明，需接续时进入当前事项；已有 `test-policy.json` 继续兼容。记录以下信息，不强制另建覆盖率策略文件。未指定模式时保持 `UNSPECIFIED`：

```json
{
  "coverage": {
    "mode": "UNSPECIFIED",
    "metric": "LINE",
    "scope": {"type": "REPOSITORY", "modules": [], "paths": []},
    "threshold": null,
    "baseline": null,
    "source": "none"
  }
}
```

- `mode`：`UNSPECIFIED`、`REPORT_ONLY`、`OVERALL`、`INCREMENTAL` 或 `BOTH`。
- `metric`：默认 `LINE`。只有报告和构建工具都支持时才使用 `BRANCH`、`INSTRUCTION`、`METHOD` 或 `CLASS`，并记录实际指标。
- `scope`：仓库、模块或明确的路径集合。多模块整体结果按执行到的可执行项加权汇总，不能对模块百分比做简单平均。
- `threshold`：0 到 100 的数值，表示生效门禁共用阈值；不同门禁分别指定时使用对象，例如 `{"overall":75,"incremental":80}`。对象只支持 overall/incremental，必须包含当前模式需要的键和值；`null` 表示尚未指定，不能据此判断数字门禁通过。比较原始值 `>=` 阈值，不先四舍五入。
- `baseline`：增量模式必填，使用用户指定的分支、提交或 merge-base，并记录解析后的 commit。无法稳定解析时不能降级成整体覆盖率。
- `source`：`existing-policy`、`user`、`none` 等真实来源，推荐值与用户要求分别记录。

`INCREMENTAL`/`BOTH` 的 policy 缺少非空 baseline 时结构校验失败，不能当作可用增量策略；Agent 仍需解析真实 commit、核对源码映射与报告，校验器只检查已声明字段。

## 五种模式

| 模式 | 行为 | 通过条件 |
|---|---|---|
| `UNSPECIFIED` | 不新增采集、阈值或阻断；读取仓库已有门禁 | 既有门禁按其自身规则判断；没有既有门禁则 `NOT_APPLICABLE` |
| `REPORT_ONLY` | 生成并展示匹配本次代码的覆盖率报告 | 报告可用则展示数值；不因阈值阻断，但报告缺失仍记 `UNKNOWN` |
| `OVERALL` | 对指定范围的全部可执行代码计算整体覆盖率 | 报告完整且每个生效指标达到阈值 |
| `INCREMENTAL` | 只计算基线到当前版本之间新增或修改的可执行代码 | 有可执行变更行且映射、报告和阈值均有效，并达到阈值 |
| `BOTH` | 独立计算整体与增量两道门 | 两道门都通过；其中一项 `UNKNOWN` 或 `BLOCKED` 时整体不能报通过 |

用户只说“看一下覆盖率”时使用 `REPORT_ONLY`，不自设数字。用户没有提覆盖率时使用 `UNSPECIFIED`，但不能绕过仓库原有的强制门禁。

## 整体覆盖率

使用当前同一份源码、构建产物和覆盖率报告。多模块或多路径汇总使用可执行项的总分子/总分母；模块级门禁逐项判断。报告缺模块、包含旧构建产物、与测试运行的 commit 或工作树不匹配时记 `UNKNOWN`，不能用部分结果填充整体百分比。

## 增量覆盖率

先解析并记录基线 commit，再计算 diff。只纳入新增或修改的可执行行；删除行、注释、空白和纯资源文件不纳入分母。修改行能映射到报告中的当前源码时才可判定。没有可执行变更行记 `NOT_APPLICABLE`，不计为 100%；源码映射、基线或报告不可靠记 `UNKNOWN`。增量行与整体行覆盖率不能互相替代。

增量策略应在报告中列出基线、变更文件、纳入的可执行行数量、排除原因、映射状态和实际命令。对于重命名、生成代码、宏/编译器变换或跨模块映射，无法证明对应关系时扩大验证或报告 `UNKNOWN`。

## 质量门与执行范围

覆盖率策略只在测试和报告来自同一代码版本、同一构建配置且报告新鲜时生效。测试失败、必需套件跳过、报告陈旧、范围不完整或环境阻塞都会使相应门禁 `NOT_VERIFIED`。覆盖率通过也不能掩盖关键风险没有行为断言。

`check --fast` 可以只执行变更相关套件，但不能据此声称整体门已通过；`check --full` 也不会自动引入仓库没有要求的工具或阈值。`pipeline` 优先复用已验证的采集命令和门禁；草稿可包含有仓库依据但尚未执行的命令，必须标待验证。候选写清模式、阈值、基线、报告路径和运行环境；未验证的门禁不能支撑 finalize 或完整通过结论。
