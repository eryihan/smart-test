# 从业务行为到测试

适用于存量缺口分析、变更用例设计和断言评估。框架能力按项目核对，Java 接入见 [java-testing.md](java-testing.md)，执行见 [verification.md](verification.md)。

## 明确要保护的行为

从需求、协议、已确认规则和可信历史测试中确认：输入与前置状态、成功结果、拒绝或失败结果、持久化及外部副作用。实现用于定位路径与边界，不能自动成为预期。来源冲突时保留差异；只有重构保护且无已知冲突时，才将当前行为作为明确标注的 characterization。

把变更文件关联到行为。例如 Mapper XML 的 JOIN 变化可能影响结果基数和分页；状态条件变化可能影响非法转换与重复请求；公共错误处理变化可能影响多个 API 的响应契约。优先处理业务损失大、恢复困难及新增失败路径，不按类名或行数分配用例。

## 选择场景

| 规则形态 | 推导方法 | 关键问题 |
|---|---|---|
| 金额、数量、长度、日期区间 | 等价类与边界值 | 有效区间、边界是否包含、最小单位与精度；空值是否独立处理 |
| 多条件审批、优惠、权限 | 小型决策表 | 条件组合、不可达组合、拒绝优先级；只裁剪业务确实不可能的组合 |
| 订单、审批、任务状态 | 状态转换 | 合法/非法转换、重复操作、转换后的可见状态 |
| 多步写入与外部调用 | 失败路径与副作用 | 哪一步失败、此前动作保留还是撤销、哪些后续动作不应发生 |
| 转换、聚合、规则函数 | 有依据的不变量 | 守恒、顺序或往返性质是否由协议成立；性质须有依据 |

按风险选择方法。相同规则的输入变化优先复用项目已有参数化设施；每个非法条件通常独立验证，避免一条校验掩盖另一条错误。

金额示例仅适用于已确认规则“申请金额大于 0、不得超过剩余额度、最小单位 0.01”。额度 100.00 时，候选为 -0.01、0、0.01、99.99、100.00、100.01，并检查额度为 0。拒绝后既要断言错误，也要断言申请未新增、额度未扣减。未确认精度或舍入方式时先指出缺失事实，不自动套用 0.01 或某种舍入模式。

状态示例：规则明确 CREATED 可取消、PAID 不可取消，且重复取消返回原结果。分别验证 CREATED → CANCELLED、PAID 拒绝且状态不变、CANCELLED 重复调用无第二次退款/事件。若重复语义未知，只设计已确认部分。

## 评估已有测试

沿业务入口检查代表性测试、fixture 和断言：

- **行为已覆盖**：相应输入、结果与重要副作用均有可执行断言，继续复用。
- **执行到了但断言不足**：补强现有用例。例如 assertThrows 未证明订单没有提前写入，HTTP 200 未证明返回字段正确。
- **替身只证明了部分边界**：verify(mapper.insert) 能观察调用，不能证明真实 SQL、约束或回滚；补所缺边界的测试。
- **没有发现覆盖**：先核对参数化、继承测试、其他模块与 suite，仍缺失再增加用例。

评估结果列出行为、已有证据、缺口和拟补断言，无需新增状态或文件。代码覆盖率只能帮助定位，不能证明行为被保护；不因异常断言、契约断言等没有某个关键字而判为无断言。

优先复用、补强已有测试，仍有缺口时再新增。每个测试聚焦主要行为，检查可观察结果，必要时检查关键协作，避免把私有方法和调用顺序全部锁死。

## 选择测试边界

选择能揭露目标错误的最低充分层级，核对实际加载边界：

| 风险 | 优先边界 | 必须能观察的内容 |
|---|---|---|
| 纯规则、金额、状态分支 | Unit | 输出、错误、状态与必要副作用 |
| HTTP 入参、序列化、错误码、安全过滤 | Web slice 或 API | 请求到响应及所需认证授权路径 |
| 服务内编排 | Unit 或组件 | 内部规则与协作；远程依赖可在客户端边界使用可控替身 |
| SQL、ORM、数据库约束 | 同类且兼容版本数据库 integration | 实际查询、mapping、排序/基数、约束与写入效果 |
| 事务、代理、提交后事件 | 应用事务 + DB integration | 真实事务边界内失败与边界外持久状态 |
| Redis 原子性/过期、MQ ack/重投 | 对应服务 integration | 服务端语义、隔离、失败与恢复行为 |
| 独立部署服务兼容性 | Contract | consumer/provider 协议；provider 实现另行验证 |
| 关键完整流程 | 少量 API/E2E | 主要成功路径与高损失失败路径 |

mock 不得替代被测行为或目标 SQL/事务/broker 语义。Slice 能否成立取决于所需组件是否真实加载；速度不足以成为排除关键边界的理由。不设固定 Unit/Integration/E2E 比例，完整 E2E 也不替代具体失败路径的诊断测试。

组件示例：创建订单涉及内部规则、Repository、事务和数据库，外部支付由真实客户端接可控 HTTP 服务。该边界可证明本服务的状态与支付错误映射；不能证明真实支付方实现正确。若此次改动涉及路由或安全过滤器，再从 API 入口验证。

## 专项风险的场景提示

按相关风险选择场景，Java 接入与隔离见 [java-testing.md](java-testing.md)：

- **权限与租户**：角色之外，核对对象归属、租户与操作。合法用户访问他人的资源、跨租户读写和批量接口分别检查；拒绝后无数据或副作用泄露。
- **幂等与并发**：重复同一请求、同 key 不同 payload、处理中重试；并发用可控交错触发竞争，断言最终记录/余额/事件数量。HTTP 成功或“调用一次”不足以证明最终效果。
- **远程调用**：超时、连接失败、明确失败响应、成功但客户端未收到结果。确认重试范围、错误映射和重复副作用；不要重试所有异常。
- **消息与缓存**：处理成功但 ack 失败、重复投递、事务提交与发布间失败、缓存更新失败。断言恢复后的可见状态；只出现一次异常日志不能证明补偿正确。
- **迁移**：空库与代表性旧数据升级都应覆盖；部署兼容按项目实际新旧应用共存要求判断。

幂等 key 生命周期、缓存过期窗口和消息顺序均以项目契约为准。

## 断言与维护成本

沿用项目命名与风格，以业务行为表达用例。优先检查准确结果/错误、状态、重要副作用；少用只 assertNotNull 或过度 verify。fixture 采用能区分正确与错误实现的小数据集，控制时间、随机源、共享可变状态和执行顺序；异步用有界条件等待，不靠固定 sleep。

PIT/性质测试按确定性规则、兼容设施与实际需求选用。可在隔离 fixture 中改错边界比较符、移除归属判断或回滚步骤，检查断言能否发现错误；禁止在用户业务工作区制造缺陷。

交付列明保护的行为、复用或新增的测试、实际执行范围和剩余缺口；按需保存 JSON。
